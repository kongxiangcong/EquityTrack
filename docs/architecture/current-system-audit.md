# 当前投研系统实现审计

> 历史文档：本文记录 2026-07-10 V3 重构前的实现，用于解释旧架构问题，不代表当前运行入口。当前唯一入口是 `skills/SKILL.md`。

审计日期：2026-07-10
审计范围：`skills/`、现有校验器、历史运行产物和意华股份样例。本文只描述当前代码现实，不把计划中的能力算作已实现。

## 结论

当前仓库是一个“由 Skill 文档驱动的研报生产包”，不是一个可重复执行的个人投研系统。它已经建立了较好的安全边界、来源追踪、估值方法路由和三层校验意识，但核心执行仍依赖 Agent 临场解释长篇 Markdown、临时编写 Excel/HTML 生成脚本并通过文件名传递状态。

最严重的问题不是门禁存在，而是门禁粒度错误：来源清单校验器把 23 个字段作为所有公司、所有分析方法、所有输出的统一必填集合；任一字段缺失都会让整个 manifest 失败。Task 2 和 Task 3 又把这个全局布尔值当作总开关，因此“某个方法缺输入”被放大成“整个研究流程不能继续”。意华股份已有 21/23 个字段、模型校验通过，但因为季度 D&A 和租赁负债拆分缺失，仍只能生成阻断备忘录，正是这一设计缺陷的真实复现。

可行的方向不是降低真实性要求，也不是用估算伪装事实，而是把系统拆成两类状态：

1. `manifest_integrity`：来源文件是否可读、字段/单位/期间是否自洽、是否存在冲突。这一层仍应 fail closed。
2. `capability_readiness`：某一项能力是否有足够证据，例如基础研究、盈利质量、可比估值、DCF、情景分析、条件计划。缺少方法专属字段只禁用相应能力，不应阻断其他能力。

## 当前功能完整性

| 能力 | 当前实现 | 完整度 | 主要问题 |
|---|---|---:|---|
| 请求路由 | `skills/SKILL.md` 通过问答选择 Tear Sheet、L1、L2 | 部分 | 路由是自然语言流程；没有结构化请求、默认策略或可恢复状态 |
| 数据来源规则 | 官方披露优先、source manifest、原始文件哈希 | 较强 | schema 对每个来源要求过细；没有轻量采集档与完整审计档之分 |
| 来源校验 | `source_manifest_validator.py` | 较强但粒度错误 | 所有公司固定要求 23 个字段；缺失与结构无效共享失败出口 |
| 研究分析 | 六维、行业链、收入模型、风险框架等 Markdown 方法 | 部分 | 只有方法说明，没有结构化分析结果或确定性执行接口 |
| 估值路由 | 行业矩阵、DCF applicability、同业最少数量规则 | 方法论较强 | 路由结果没有统一可执行 schema；与来源字段需求没有程序化绑定 |
| DCF | 方法文档 + Excel 校验规则 | 部分 | 没有可复用计算引擎、WACC 构建器或独立敏感性实现；模型每次临时生成 |
| 可比估值 | 同业选择和统计说明 | 部分 | 没有同业口径归一、异常值处理、倍数计算和审计结果对象 |
| 行业特化估值 | 文档覆盖金融、医药、周期、地产等 | 很低 | 没有 residual income、DDM、rNPV、NAV、mid-cycle 等可执行实现 |
| 财务模型 | `model_validator.py` 验证工作簿结构和公式 | 部分 | 校验器存在，但模型生成器不在产品代码中；大量生成器留在单次 `outputs/*/work/` |
| 情景分析 | Markdown 模板 | 很低 | 没有统一的 driver、scenario、invalidation 或 sensitivity 数据结构 |
| 条件研究计划 | 无产品实现 | 缺失 | 没有观察项、触发条件、失效条件、复核日期和风险预算的结构化结果 |
| HTML/PDF | CSS、图表脚本、报告校验器 | 部分 | 报告通常由样例专用脚本拼装；图表和正文不共享统一的 `ResearchRun` 数据源 |
| 工作流编排 | Task 1 → STOP → Task 2 → STOP → Task 3 | 很低 | 没有单命令入口、状态机、断点恢复、adapter registry 或运行日志 |
| 测试 | 少量 fixture builder 和手工 smoke 命令 | 很低 | 没有项目级测试配置、行为测试、端到端回归或 CI 入口 |

## 直接代码证据

### P0：统一 23 字段门禁造成错误的全局阻断

`skills/scripts/source_manifest_validator.py` 中的 `BASE_CRITICAL_FIELDS` 固定包含收入、EBIT、D&A、租赁负债、养老金缺口、期权稀释、汇率等 23 项。构造校验器时，这个集合直接成为默认 `required_fields`；结果函数只要存在任意 error 就令 `passed = false`。这意味着：

- DCF 专属输入会阻断只需要利润和股本的 P/E 分析；
- 企业价值桥的租赁负债会阻断不依赖 EV 的研究结论；
- `preferred_stock`、`pension_deficit` 等不适用于大量 A 股公司的字段仍需被逐项证明为零；
- 季报依法未披露的明细会被当成整个研究不可用，而不是对应方法不可用。

Task 1、Task 2 和 Task 3 随后都要求 `passed = true` 且 `source_manifest_status = sufficient` 才能继续，因此局部缺口被传播为流水线总停机。

修复方向：保留结构完整性校验，新增按 capability 定义的最小字段集合；`research_core`、`earnings_quality`、`equity_bridge`、`comps`、`dcf`、`historical_band`、`conditional_plan` 分别评估。总运行状态允许 `completed_with_limits`。

### P0：Skill 是控制平面，也是实现平面

四个入口文档同时承担请求解析、状态管理、异常处理、数据规则、估值路由和交付说明。调用者必须理解大量顺序约束，Agent 还需要临时决定文件位置、命令参数和回退路径。Skill 的不确定性因此直接进入业务结果。

修复方向：把 Skill 降为“操作手册和外部数据采集 adapter”；确定性 Python 核心持有请求、状态、门禁、方法路由、结果 schema、报告渲染和校验。Skill 只能提交结构化输入或补充叙事，不再决定状态迁移。

### P0：没有可复用的模型和报告生成实现

`skills/scripts/model_validator.py` 能检查 Excel，但仓库没有对应的模型 builder。历史模型生成代码位于各次 `outputs/.../work/*.mjs`；意华股份 HTML 也由公司专用脚本硬编码正文、数字、图表和 CSS。换一家公司就需要重新写实现，无法形成稳定产品。

修复方向：建立一个 `ResearchEngine.run(request)` 的深模块，以 `ResearchRun` 作为唯一事实源；Excel、HTML、JSON 都是同一状态的 renderer，而不是彼此转抄。

### P1：数据真实性、可用性和结论权限被混在一个布尔值里

当前 `source_manifest_status` 试图同时回答四个问题：文件是否合法、字段是否存在、来源是否足够权威、是否允许任何估值结论。一个布尔值无法表达“基础研究可靠、DCF 不可用、可比估值可用、交易触发条件仍待验证”这种现实状态。

修复方向：每个字段记录 `provenance`、`quality`、`freshness`、`derivation` 和 `materiality`；每个 capability 返回 `ready`、`ready_with_estimates`、`limited` 或 `blocked`，并列出只影响该能力的缺口。

### P1：估值方法文档覆盖面大，但执行完整性低

当前方法路由对金融、医药、周期、地产、SaaS 等特殊行业的方向基本合理，DCF 文档也包含 FCFF、WACC、终值和敏感性要求。然而这些规则没有可执行对象，无法保证：

- 方法输入与 manifest 字段需求一一绑定；
- 计算的单位、币种、期间和股权桥一致；
- 方法被禁用后不会在临时报表脚本中重新出现；
- 多方法结果使用一致的情景和估值日期；
- 估值区间的不确定性来自真实 driver，而非任意上下浮动。

另外，文档将 DCF、历史估值带和敏感性称为“mechanically inseparable”并不准确。DCF 的 WACC × g 敏感性与 DCF 机械相连，但历史估值带是独立的 relative-to-self 方法，不应因为 DCF 输入缺失而被禁用。

修复方向：以 method registry 表达 `applicability`、`required_capabilities`、`calculate`、`diagnostics` 和 `render`；先落地可比估值、历史带和通用 DCF，再逐步增加行业模型。

### P1：报告 QA 偏重形式标记，不验证数据链

现有 `report_validator.py` 检查标题、关键词、图表数量、CSS 类和文本标记，能防止空壳报告，却无法证明图表与表格来自同一版结构化数据，也无法判断一项结论是否引用了支撑它的证据。

修复方向：报告 renderer 只接收 `ResearchRun`；每个 exhibit 和结论携带 `evidence_ids`；HTML 中输出机器可读的 provenance 标记。QA 同时验证结构、数据引用、禁用方法泄漏和禁止性语言。

### P1：没有真正的“个人研究计划”模块

项目目前在“研究报告”和“投资建议”之间摆动，但缺少可审计的中间表达。直接输出买卖指令既不安全，也无法复盘；只输出散文又无法形成执行纪律。

修复方向：输出非个性化的 `conditional_research_plan`：观察变量、验证触发、失效条件、最大数据陈旧度、复核日期、事件风险和待补证据。它描述“什么变化会改变研究视角”，不替用户决定具体交易。

### P2：工程基础设施缺失

- 没有 `pyproject.toml`、安装入口或统一 CLI；
- 没有包级日志、错误码和运行目录约定；
- 没有测试发现入口和端到端 fixture；
- 生成物、上游研究仓库和产品代码没有清晰隔离；
- 大型 Markdown 中存在重复规则和容易漂移的交叉引用。

## 方法论判断

### DCF

当前 DCF 方法的 FCFF/WACC、`WACC > g`、金融企业禁用普通 FCFF DCF、周期企业使用中周期假设等原则是合理的。问题主要在实现和适用性粒度，而非公式框架本身。

需要调整的地方：

- “最新季度 D&A”不应自动成为所有 DCF 的绝对前置条件；可使用最近年度官方明细建立预测基线，并把季度缺口计入置信度，但是否允许正式输出应由 materiality 和估算占比决定；
- 租赁负债应根据行业、会计处理和估值倍数定义决定是否纳入净债务，不应全局必填；
- “终值通常占 EV 50%-70%”只能是诊断提示，不能作为硬真理；高增长或资本轻公司可能自然更高，但必须披露敏感性；
- WACC 不应采用静态市场典型区间作为主要判断，应该由无风险利率、ERP、beta、债务成本和资本结构逐项形成证据链；
- 反向 DCF 应作为优先级较高的市场预期诊断，它对缺少长期预测时比强行给出点估值更稳健。

### 可比公司法

至少 3 个可用同业是合理的结论门槛，但应只阻断可比估值能力。还需要程序化实现同业筛选理由、会计口径、币种、估值日期、异常值、负分母和生命周期差异。目标不是凑满 5-10 家，而是保留足够同质且可审计的样本。

### 历史估值带

历史带可以在 DCF 被禁用时独立工作，但必须做复权价格、滚动分母、会计重述、亏损期和周期陷阱处理。对周期股，P/E 在盈利高点会机械变低，不能直接解释为便宜。

### 情景与风险

当前文档有 bull/base/bear 形式，但缺少 driver 级联动和情景失效条件。新的实现应将情景定义为一组可追踪假设，不默认分配概率；只有概率有证据基础时才允许加权。

## 重构优先级

1. 建立 `ResearchRequest -> ResearchRun` 单一接口和可恢复运行状态。
2. 将来源校验拆为完整性校验与 capability readiness。
3. 用 method registry 连接估值方法、字段要求和输出权限。
4. 让 Task 1 不再是总门禁：最小基础研究数据满足时即继续，缺口进入局部限制。
5. 建立通用 HTML renderer 和结构化报告 schema，删除公司专用生成脚本模式。
6. 增加意华股份端到端回归：预期基础研究和情景计划可生成，DCF 因专属输入不足而受限，整个流程不再阻断。
7. 再扩展数据 adapter、完整估值计算、回测/组合和自动化能力。

## 本轮边界

本轮重构可以把仓库变成可执行、可扩展、可测试的研究内核，并用现有意华股份数据验证新的降级行为。它不会连接券商下单，也不会产生个性化买卖指令。任何数值估值仍必须遵守方法专属数据要求和来源追踪。
