## Definitions / 关键定义

为避免概念混用，统一采用以下定义：

* **事实（fact）**：能够追溯到明确数据源、发布日期、可用时间和抓取时间的信息。
* **假设（assumption）**：模型输入中无法直接观测或需要主观设定的变量，必须显式记录来源、范围和理由。
* **推演（forecast / thesis evolution）**：从事实和假设出发，给出因果链、时间范围、领先指标、概率、失效条件和更新规则的可证伪判断；不是笼统看多或看空。
* **估值（valuation）**：由确定性代码计算的模型结果。叙述可以由 Codex 组织，但数值、公式、单位和敏感性分析不得由语言模型凭空生成。
* **交易计划（trade plan）**：包含入场、加减仓、退出、失效、风险预算和市场条件的版本化决策规则；不是一句“建议买入/卖出”。
* **交易策略（strategy）**：可执行、可回测、输入输出明确的信号、仓位、风险和执行规则组合；自然语言观点本身不是策略。
* **回测（backtest）**：严格遵守信息可用时间、交易规则、费用和滑点的历史模拟；使用未来数据、修订后数据或同一数据同时调参和验收的结果不算有效回测。
* **动态工作流（dynamic workflow）**：依据任务类型、标的特征、数据可用性和风险约束动态选择节点的可组合工作流。它不是在业务代码中硬编码一段 LLM prompt。
* **完成（complete）**：实现、迁移、测试、文档、可追溯数据和验收用例全部通过，而不是“核心代码大致完成”。

## Non-negotiable constraints / 不可违反的约束

1. **Codex 是控制面，业务运行时不得内置 LLM 调用。**

   * 禁止在应用代码中调用 OpenAI、Anthropic、Gemini、Kimi、DeepSeek 或其他 LLM API。
   * 禁止在业务运行时代码中硬编码用于模型分析的自然语言 prompt。
   * 允许在 Codex/Skill 层存在操作说明、模板和编排规范；确定性数据处理、财务计算、估值、策略规则、回测和计划评估必须由普通代码完成。
2. **用户不手动执行 CLI。**

   * Codex 必须能够通过一个稳定入口完成初始化、数据同步、每日任务、启动平台、健康检查、迁移、测试、备份和恢复。
   * 可以存在 CLI 或脚本，但它们是 Codex 调用的维护接口，不应要求用户记忆和手工执行零散命令。
   * 仓库位于 Windows 路径，核心维护入口必须跨平台；不得只提供 Bash/Makefile 方案。
3. **本地优先与隐私优先。**

   * 个人账户、现金、持仓、交易记录、交易计划和注释默认只存本地。
   * 禁止默认遥测，禁止把持仓或密钥发送到无关第三方。
   * 密钥不得进入源码、数据库明文日志或 Git 历史。
4. **不得破坏现有工作。**

   * 首先检查 `git status`、未提交修改和现有测试。
   * 禁止无授权执行破坏性 reset、clean、覆盖或大规模重写。
   * 优先通过适配层整合现有投研报告 MVP，模块分析补充，而不是重新实现一套并行系统。
5. **当前范围不包含真实自动下单。**

   * 可以设计纸面交易、模拟成交和未来券商适配接口。
   * 本轮不得接入真实账户下单，不得把“交易计划”偷偷扩展为自动执行。
6. **所有关键输出必须可追溯、可复现。**

   * 记录数据源、数据版本、`as\_of`、`published\_at`、`available\_at`、`retrieved\_at`、模型版本、代码版本、参数、随机种子和运行 ID。
   * 缺失数据必须显式标识，不得静默填造。

## Target system capabilities / 目标系统能力

### 1\. 股票投研分析

股票分析必须拆成可独立运行、可缓存、可审计的模块，至少包括：

* 公司与证券主数据：代码、交易所、币种、行业、上市状态、公司行动。
* 公司基本情况：业务分部、商业模式、地区、客户、竞争优势、治理和资本配置。
* 基本面：收入、利润、现金流、资产负债表、盈利质量、资本开支、营运资本、ROIC/ROE、杠杆、稀释和分红回购。
* 技术面：复权一致的 OHLCV、趋势、波动率、成交量结构、关键区间、相对强弱和市场状态；技术指标只能作为证据之一，不得伪装成确定性预测。
* 行业与同业对比：明确同业选择规则，按业务结构、地区、规模、盈利能力和成长阶段归一化比较。
* 估值：根据公司类型动态选择 FCFF、FCFE、DDM、剩余收益、相对估值、SOTP、资产价值或周期中枢方法；不得机械地对所有公司套同一个 DCF。
* 上下游与产业链：供应、产能、利用率、价格、库存、客户集中度、议价权、替代品、渠道和关键约束。
* 催化剂与风险：事件、时间窗口、影响路径、概率和可观察指标。
* 证据质量：区分官方披露、监管/交易所、行业数据、媒体、社交信息和主观判断。

每个模块必须同时输出：

1. 机器可读的结构化结果；
2. 人类可读的 Markdown/HTML；
3. 数据与证据清单；
4. 假设和缺口；
5. 模块版本与运行记录。

最终报告必须区分“事实、计算、假设、判断、风险”，不得把它们混成一段结论。

### 2\. 公司发展推演与预测复盘

从两个示例文档中提炼通用方法，而不是照抄个股结论。每条推演至少包含：

* 可证伪的核心命题。
* 因果链和驱动树。
* 时间范围和关键里程碑。
* 基准、乐观、悲观或其他必要场景；概率总和应一致。
* 对收入、销量、产能、利用率、ASP、成本、利润率、资本开支、现金流或行业变量的量化假设。
* 假设分布、变量相关性和证据来源。
* 领先指标、更新频率、触发条件和失效条件。
* 预期结果区间，而不是单一点估计。
* 后续真实结果和误差分解。

建立预测登记表和复盘机制。至少记录：

`forecast\_id, security\_id, created\_at, as\_of, horizon, claim, drivers, assumptions, scenarios, probability, expected\_range, indicators, triggers, invalidation, review\_date, status, actual\_outcome, error\_analysis`。

对概率事件可使用 Brier Score；对数值预测至少记录绝对误差、相对误差、区间覆盖率和方向判断。复盘必须保留原始预测版本，禁止事后改写历史假设。

### 3\. 估值建模

估值计算必须由确定性代码完成并经过单元测试。至少支持：

* FCFF/FCFE 多阶段模型、WACC、终值和敏感性分析。
* 相对估值与同业统计分布。
* 适用时的 SOTP、DDM、剩余收益或周期化估值。
* 基准/乐观/悲观场景和 Monte Carlo 分布。
* 每股价值桥接，包括净债务、少数股东权益、非经营资产、股本稀释和币种换算。

模型必须保存公式、输入、单位、来源、日期、选择理由和计算过程。银行、保险、券商、资源品、亏损高增长公司等特殊行业必须使用适合其经济结构的方法，不能机械套用工业企业 FCFF。

### 4\. 个人账户、持仓和观察池

平台至少支持：

* 多账户、基础币种、现金流水、交易流水、持仓批次、成本、手续费、税费、分红、拆并股和其他公司行动。
* 已实现/未实现盈亏、时间加权收益、资金加权收益、基准比较和组合快照。
* 持仓池、观察池、标签、优先级、投资逻辑、风险、催化剂和复核日期。
* 用户风险配置：投资期限、最大单股/行业仓位、单笔风险、最大组合回撤、杠杆许可、流动性下限和现金保留要求。
* 单股、行业、市场、币种和风格暴露；集中度、流动性和风险预算。
* 每日不可变快照和完整审计日志。

数据库必须保证交易、现金、持仓和组合净值可对账。除非明确启用融资融券，否则不得静默允许负现金或超额持仓。

### 5\. K 线和分析标注

K 线能力至少包括：

* 日/周/月及必要的分钟周期。
* 前复权、后复权和不复权语义明确且一致。
* 成交量、常用指标、基准或同业对比。
* 用户绘制的趋势线、水平线、区间、文字、事件和交易标记。
* 投研报告、预测里程碑、实际交易和交易计划触发点的图上关联。
* 标注持久化、版本、创建时间、作者、价格坐标、时间坐标和所用复权模式。

必须对 `TradingView Lightweight Charts`、`KLineChart` 和 `ECharts` 做能力与许可证比较。不得把 TradingView 的所有产品笼统当成开源库；采用任何库前必须核验许可证、NOTICE 和归属要求。

### 6\. 交易计划生成与追踪

交易计划应基于投研结论、估值分布、技术结构、流动性、个人风险约束和市场状态生成草案，并由用户确认后进入激活状态。计划至少包含：

* 计划目的、持有周期和对应投资逻辑。
* 入场区间、触发条件、初始仓位和最大仓位。
* 加仓、减仓、止损、止盈、移动保护和失效规则。
* 单笔风险、组合风险、最大可接受亏损和流动性约束。
* 财报、解禁、政策、行业价格等事件风险。
* 计划依赖的市场状态和禁止交易条件。
* 证据、数据快照和计划版本。

采用明确状态机，例如：

`draft -> approved -> active -> triggered -> partially\_executed -> completed / invalidated / cancelled`。

每日评估必须由结构化规则引擎完成，输出“触发了什么、未触发什么、使用了哪份数据、为何建议保持或调整”。任何调整都创建新版本，不得覆盖旧计划或用后见之明重写理由。

### 7\. 策略建模、回测和模拟

必须把策略拆成四个相互独立但可组合的层：

1. 信号生成；
2. 仓位分配；
3. 风险管理；
4. 执行模拟。

研究流程必须从可证伪假设和基线策略开始，不得直接进行大规模参数搜索。至少处理：

* 前视偏差、幸存者偏差、样本选择偏差和数据窥探。
* 财务数据、公告和宏观数据的真实发布时间与可用时间。
* 复权、停牌、退市、交易日历、时区和币种。
* 交易费用、税费、买卖价差、滑点、成交量约束和冲击成本。
* 目标市场特有规则；例如 A 股的 T+1、涨跌停、最小交易单位和特定税费必须在适用时建模。
* 日线收盘数据生成的信号默认不得在同一收盘价无摩擦成交；必须明确下一个可成交时点。
* 训练、验证、测试或滚动样本外评估；禁止在同一时期反复调参后把最优结果当作样本外结果。
* 参数稳定性、不同市场状态、不同标的和成本扰动下的鲁棒性。
* 与简单基线、基准指数和买入持有的比较。

至少输出：收益、波动、Sharpe、Sortino、最大回撤、Calmar、换手率、胜率、盈亏比、暴露、Beta、VaR/CVaR、成本敏感性和样本外稳定性。不要只优化一个漂亮指标。

每次研究必须登记：

`strategy\_version, data\_snapshot, code\_commit, parameters, random\_seed, universe, benchmark, execution\_model, cost\_model, train\_period, test\_period, metrics, artifacts, conclusion`。

### 8\. Monte Carlo 与情景模拟

Monte Carlo 不是所有问题的默认答案。必须先说明模拟对象和不确定性来源。

* 对公司经营和估值，优先模拟业务驱动变量，如需求、产能爬坡、利用率、ASP、成本、毛利率、资本开支、营运资本、WACC 和终值增长率。
* 对价格路径和交易风险，可使用历史区块自助法、状态条件分布、波动率模型或其他有证据的过程；不得无解释地假设独立同分布正态收益或直接套 GBM。
* 必须建模关键变量相关性，说明分布如何校准，并提供敏感性和压力场景。
* 保存随机种子、样本数、收敛检查和分位数结果。
* 输出价值区间、收益分布、最大回撤分布、触发概率、破产/超限概率和关键变量贡献。
* 模拟结果必须用后续真实数据进行校准和复盘，不能只生成一次漂亮图表。

### 9\. 大盘、市场热度和宏观跟踪

市场分析必须从透明组件构成，至少覆盖：

* 指数趋势和相对强弱。
* 成交额、换手和流动性。
* 上涨/下跌家数、创新高/新低、涨跌停等市场宽度指标，在适用市场中使用。
* 波动率、相关性、拥挤度和行业轮动。
* 资金、情绪、新闻和事件，但不得把社交热度当成事实。
* 利率、信用、汇率、商品、通胀、增长和政策等与目标市场相关的宏观变量。

建立可解释的市场状态模型，例如由趋势、宽度、流动性、波动和情绪构成的状态或评分。每个分项都必须有定义、窗口、归一化方法和历史分布，不能只输出一个无法解释的“热度分”。

每日生成不可变的 `market\_snapshot`，并记录与前一日相比的变化归因。个股交易计划必须能引用该快照作为门控条件。

## Data architecture / 数据架构要求

采用分层数据设计，至少区分：

1. **Raw**：原始响应或原始文件，不可变保存，带来源和抓取元数据。
2. **Normalized**：统一证券、时间、币种、单位、复权和字段语义后的标准数据。
3. **Derived**：指标、特征、估值、场景、市场状态和策略信号。
4. **Artifacts**：报告、图表、回测结果、模型文件和审计清单。

最低实体范围应覆盖：

* `security\_master`, `market\_calendar`, `ohlcv`, `corporate\_action`；
* `financial\_fact`, `filing`, `industry\_peer`, `supply\_chain\_entity`, `macro\_series`, `news\_event`；
* `research\_run`, `research\_evidence`, `valuation\_model`, `scenario`, `forecast`, `forecast\_review`；
* `account`, `cash\_ledger`, `transaction`, `position\_lot`, `portfolio\_snapshot`, `watchlist`, `watchlist\_item`；
* `chart\_annotation`；
* `trade\_plan`, `trade\_plan\_version`, `plan\_rule`, `plan\_evaluation`；
* `strategy`, `backtest\_run`, `model\_artifact`；
* `market\_snapshot`, `workflow\_run`, `artifact\_manifest`。

数据库选择必须基于当前仓库和单用户场景做决策。默认优先考虑简单、可迁移的模块化单体；不要在没有并发和规模证据时过度设计微服务。可评估 SQLite/PostgreSQL 处理事务元数据、DuckDB/Parquet 处理本地分析型时序数据，但不得无理由同时引入多套存储。

数据接入必须具备：

* Provider 适配接口和字段契约。
* 来源优先级、回退策略、限流、重试和熔断。事实数据优先使用上市公司、交易所、监管机构和官方宏观来源；第三方聚合源必须保留原始出处与能力边界。
* 增量同步、幂等写入、内容哈希、TTL 和强制刷新。
* 数据质量检查：重复、缺失、OHLC 合法性、异常跳变、交易日历、单位、币种、复权和公司行动一致性。
* 离线缓存运行能力；第二次执行不得重复抓取或重复入库。
* 明确的数据许可和使用边界。

## Dynamic workflow and Codex entry / 动态工作流与入口

建立一个可版本化、可恢复的工作流注册表。典型节点可以包括：

`resolve\_security -> ingest -> validate -> normalize -> analyze -> model -> simulate -> synthesize -> adversarial\_audit -> persist -> publish`。

要求：

* 节点具有明确的 typed input/output、版本、前置条件、缓存键和失败语义。
* 工作流根据任务、标的类型、数据可用性和用户配置选择节点，不要求所有股票都执行相同模型。
* 节点尽量幂等，并产生统一 `artifact\_manifest`。
* 失败后可从已完成节点恢复，不能每次从头抓取全部数据。
* 业务代码中不得包含 LLM prompt；Codex 在外部读取 Skill 和结构化产物后完成必要的叙述与编排。

仓库必须提供：

* 根目录 `AGENTS.md`：Codex 的唯一项目操作说明。
* 一个统一 Skill 入口，例如 `skills/trading-platform/SKILL.md`，负责动态选择已有与新增技能。
* 一个跨平台维护入口，例如 `scripts/platform.py` 或等价工具，至少支持 `bootstrap / doctor / migrate / sync / daily / serve / test / backup / restore`。
* 配置模板、数据库迁移、日志、运行 ID、健康检查和故障恢复说明。
* 必要时提供本地 Web 界面用于 K 线、标注、持仓、计划和历史结果；用户无需手动拼接启动命令，Codex 应负责启动并报告入口。

## Architecture principles / 架构原则

* 优先采用模块化单体和清晰边界，除非审计证明需要其他架构。
* 确定性计算与自然语言叙述严格分离。
* 数据提供商、估值模型、分析模块、策略、执行模型、图表和报告渲染均通过稳定接口扩展。
* 生产代码不依赖 Notebook；Notebook 仅可作为研究草稿，成熟逻辑必须迁入可测试模块。
* 不做大爆炸式重写；每一步都应保持现有 MVP 可用。
* 所有模式变更使用迁移，不允许靠删除数据库重新开始。
* 日常任务必须幂等；重复运行同一天任务不得产生重复交易、快照或报告。
* 依赖应固定版本，并输出第三方许可证清单。

## Multi-agent research and implementation heuristics / 多路径协作规则

在环境支持并行子任务或子 Agent 时，动态使用，不要固定分配“若干 Agent 做某个方向”。若没有并行能力，也要以相互独立的多轮评估模拟同样过程。

* 初期保持多条独立路线：产品与用户流程、数据与缓存、财务与估值、公司推演、量化回测、风险与组合、K 线交互、架构与运维。
* 建立明确的“方法家族注册表”，按核心思想分组，而不是按措辞分组。
* 不要提前告诉多数研究者当前偏好的数据库、图表库或回测框架，避免全部收敛到第一个看起来漂亮的方案。
* 如果某条路线停在高风险缺口，例如数据许可不清、回测前视、运行时必须依赖 LLM、Windows 不支持或维护成本过高，将其标记为 blocked。只有出现实质性新证据或新机制时才重新打开。
* 独立路线充分暴露优缺点后再交叉借鉴。
* 每个研究者必须返回代码位置、接口、数据模型、公式、测试结果、许可证或可复现实验；拒绝“项目很成熟”“应该可行”之类状态汇报。
* 根任务应持续综合、质疑、重定向和收敛，不能在第一轮调研后立刻拍板。

## Adversarial audits / 对抗性审计

任何候选架构、模型、策略或纵向切片在被接受前，都必须经过至少以下审计视角：

1. **财务与估值审计**：单位、币种、会计口径、重述、股本稀释、净债务桥接、终值占比、敏感性和行业适配是否正确。
2. **数据时间审计**：是否使用了当时尚不可得的数据、修订数据、未来成分股、错误复权或错误交易日历。
3. **量化审计**：是否存在前视、过拟合、数据窥探、成本缺失、同收盘成交、参数脆弱或不合理分布假设。
4. **组合与风险审计**：现金和持仓能否对账，风险预算是否可执行，是否忽略相关性、流动性和尾部风险。
5. **软件与运维审计**：幂等性、迁移、恢复、缓存失效、日志、跨平台、并发和测试是否成立。
6. **安全与许可证审计**：密钥、隐私、遥测、数据许可、开源许可证和归属要求是否满足。
7. **工作流审计**：是否偷偷引入 LLM API 或硬编码 prompt；Codex 入口是否真实可用；用户是否仍需手工执行零散命令。
8. **后见之明审计**：预测、交易计划和研究结论是否保留原始版本，是否在看到结果后改写历史理由。

审计必须返回具体失败用例、反例或测试，不接受“整体看起来没问题”。

## Mandatory implementation tests / 强制测试

第一条纵向切片至少具备：

* 单元测试：估值公式、持仓会计、计划规则、市场状态组件和数据转换。
* 数据契约测试：Provider 返回字段、日期、单位、币种和复权语义。
* 幂等性测试：同一同步或每日任务执行两次不重复入库。
* 缓存测试：有新数据时增量刷新，无新数据时使用缓存，断网时能够读取已有数据并明确陈旧程度。
* 迁移测试：空库初始化和已有库升级。
* 回测反前视测试：构造故意泄漏的样例并确保被检测或禁止。
* 交易规则测试：至少覆盖目标市场的一个特殊规则。
* K 线标注持久化测试：刷新页面或重启后标注仍存在且坐标正确。
* 交易计划版本测试：修改计划创建新版本，旧版本不可变。
* 端到端测试：从标的选择到数据、报告、K 线、计划评估和历史回看。
* 回归测试：现有投研报告 MVP 的核心用例仍然通过。

测试用 fixtures 可以使用静态数据，但生产路径不得伪装使用假数据。真实数据源不可访问时，要明确标记为外部阻塞，并完成适配器、契约和 fixture 测试，不能声称真实同步成功。

## What does not count / 以下结果不算完成

以下任何一项单独出现都不足以完成任务：

* 只给产品愿景、架构图或 TODO 列表。
* 只复制参考项目结构或把整个外部项目作为依赖。
* 只做静态页面、假数据仪表盘或不可持久化的 K 线示例。
* 只生成自然语言股票报告，没有结构化数据、证据和可复现计算。
* 让 LLM 直接输出 DCF、概率、买卖点或仓位数字，而没有确定性计算路径。
* 使用任意分布做 Monte Carlo，却没有校准、相关性、敏感性和真实复盘。
* 回测未处理信息发布时间、复权、费用、滑点、停牌或目标市场规则。
* 在同一数据集调参并宣称样本外有效。
* 交易计划没有状态、版本、失效条件和历史审计。
* 缓存只保存文件但没有版本、TTL、幂等和失效策略。
* 要求用户手动运行多个不稳定 CLI 命令才能使用平台。
* 引入 LLM API、硬编码分析 prompt 或把个人持仓发送到第三方。
* 因为某个参考项目流行就采用，而没有许可证、维护性和集成证据。
* 只报告当前方法失败、问题复杂或需要以后再做，而没有继续寻找可执行的替代路线。

## Completion and return conditions / 返回条件

不要因为第一种方案失败、某个库不适用或某个数据源暂时不可用就提前返回。继续评估其他路线，并优先做可逆、可测试的决策。

仅在以下条件同时满足时，才将本轮标记为完成：

1. 当前项目审计和开源调研有证据支撑。
2. 架构、数据模型、工作流和路线图与实际代码一致。
3. 现有投研报告 MVP 未被破坏，并通过回归测试。
4. 第一条纵向切片真实运行，所有关键数据和产物能够持久化、回看和追溯。
5. 业务运行时代码中不存在 LLM API 调用或用于分析的硬编码 prompt。
6. 强制测试通过；未通过项有明确失败日志，不能被描述为完成。
7. 所有外部阻塞都精确说明需要的凭据、许可、数据或用户决策；不得伪造成功。

最终回复只需要给出高信息密度的交付摘要：

* 当前项目真实状态与关键发现。
* 调研后的采用/改造/拒绝决策。
* 最终架构和主要数据流。
* 已修改文件和实现的纵向切片。
* 执行过的测试及结果。
* 仍存在的已知风险、外部阻塞和下一阶段最小目标。

不要返回泛泛的“最佳实践”总结、未验证的乐观判断或把长期目标误报为已经完成。
